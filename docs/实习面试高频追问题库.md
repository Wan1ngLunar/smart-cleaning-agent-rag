# 智扫通实习面试高频追问题库

> 本题库根据项目真实实现、Git 提交历史和评测结果整理。回答时应先给结论，再解释原因和验证数据。不要背成论文，也不要把固定评测结果夸大成生产保证。

## 0. 优化前原项目基础必会题

这一部分先考察你是否真正读懂初始提交 `410d5d8`。如果只会背优化指标，却说不清原项目如何运行，面试官很容易判断你只熟悉最终文档。

### OQ1：优化前的项目已经具备哪些能力？

**参考回答：**

原项目已经有 Streamlit 聊天页面、LangChain Agent、7 个工具、Chroma 向量检索、TXT/PDF 入库、MD5 去重、通义聊天与 Embedding 模型，以及通过中间件切换报告 Prompt 的能力。它能完成知识问答、演示天气和用户上下文、CSV 使用记录查询及报告生成。后续工作是把课程原型变成稳定、可复现、可评测和可部署的项目，不是从零重写。

### OQ2：原项目的一条知识问答怎样执行？

**参考回答：**

Streamlit 获取问题后调用 `ReactAgent.execute_stream()`。Agent 模型根据工具描述选择 `rag_summarize`，RAG 工具再通过 Chroma 取 Top-3，把问题和片段交给聊天模型总结，工具结果返回 Agent 后生成最终回复，最后由 Streamlit 逐字显示。

### OQ3：原项目为什么可能有多次模型调用？

**参考回答：**

第一次调用用于 Agent 判断是否以及怎样调用工具；RAG 工具内部还有一条总结链，会调用聊天模型根据检索资料生成内容；工具结果返回后，Agent 通常还要继续调用模型组织最终答案。因此 Agent + RAG 的一次用户请求不等于一次模型调用。

### OQ4：原项目注册了哪些工具？

**参考回答：**

共 7 个：知识库检索 `rag_summarize`、天气 `get_weather`、用户城市 `get_user_location`、用户 ID `get_user_id`、月份 `get_current_month`、CSV 记录查询 `fetch_external_data`，以及用于切换报告场景的 `fill_context_for_report`。

### OQ5：`fill_context_for_report` 为什么也是一个工具？

**参考回答：**

它不负责返回业务数据，而是充当流程标记。工具成功后，中间件把运行时上下文中的 `report` 设为 `True`，动态 Prompt 中间件在下一次模型调用前改用报告 Prompt。它展示了工具调用也可以改变 Agent 后续控制流。

### OQ6：原项目的动态 Prompt 怎样切换？

**参考回答：**

Agent 每次执行时传入 `context={"report": False}`。调用 `fill_context_for_report` 后，工具中间件修改这个值；`report_prompt_switch` 在模型调用前读取它，`True` 返回报告 Prompt，否则返回普通客服 Prompt。

### OQ7：原 Streamlit 页面保存了消息，为什么还说没有真正多轮记忆？

**参考回答：**

`st.session_state["message"]` 只用于页面重新渲染历史。`execute_stream()` 每次构造的新输入中只有当前问题，没有把历史重新传给模型，也没有 LangGraph Checkpointer。因此用户能看见旧消息，但模型推理时不一定知道旧消息，应用重启后也无法恢复。

### OQ8：原项目的文档如何入库？

**参考回答：**

扫描 `data/` 下的 TXT 和 PDF，计算文件 MD5，未处理过的文件通过 `TextLoader` 或 `PyPDFLoader` 读取，再用递归文本切分器按约 200 字符、20 字符重叠切片，生成 Embedding 后写入 Chroma，成功后保存 MD5。

### OQ9：为什么文档要切分，为什么还要重叠？

**参考回答：**

整份文档太长且主题混杂，不适合直接计算和检索。切成较小片段能提高定位精度。重叠用于保留切分边界两侧的上下文，避免一句完整答案刚好被截断成互不完整的两段。

### OQ10：原项目的 MD5 去重有什么作用？

**参考回答：**

MD5 相当于文件内容指纹。已经记录的 MD5 会被跳过，避免每次运行都把同一文档重复写入 Chroma。原实现还把 MD5 放在向量写入成功之后保存，这个提交顺序能让失败文件下次继续重试。

### OQ11：原来的 RAG 检索是什么算法？

**参考回答：**

只有 Chroma 向量检索，使用 `as_retriever()` 返回 Top-3。没有 BM25、RRF、重排序、最低分过滤和固定评测基线，因此能完成基本语义问答，但无法量化精确关键词和排序困难样本。

### OQ12：原 RAG Prompt 已经要求不编造，为什么后来还要拒答机制？

**参考回答：**

Prompt 约束是软约束，而且检索器即使面对知识库外问题也可能返回三个“最相似但不适用”的片段。原服务没有空片段保护、分数粗过滤和统一资料不足协议，所以模型仍可能把相似知识迁移到错误对象上。

### OQ13：原项目如何处理来源？

**参考回答：**

它把每个 Document 的正文和完整 metadata 拼到 Prompt 中，但最终答案没有由程序建立稳定的编号、文件名和 PDF 页码映射。因此模型虽然看见元数据，用户仍没有可靠、统一的引用格式。

### OQ14：原项目的用户、城市和月份数据有什么问题？

**参考回答：**

城市在深圳、合肥和杭州中随机，用户 ID 在 1001～1010 中随机，所谓当前月份也在 2025 年随机。它们能制造演示变化，但同一问题不可复现，还可能随机到没有 CSV 记录的组合。更严重的是 Prompt 把它们描述成真实身份、真实位置和当前月份，与代码能力不一致。

### OQ15：原天气工具真的访问实时天气服务了吗？

**参考回答：**

没有。函数无论城市是什么都返回固定的晴天、26 摄氏度等字符串，但原工具描述称它能获取实时天气。后来明确改成“演示天气数据”，重点是让接口声明和真实能力一致。

### OQ16：原项目的 CSV 数据结构是什么？

**参考回答：**

加载后形成 `external_data[user_id][month]` 两层字典，值包含特征、效率、耗材和对比。首次查询时读取 CSV，之后复用进程内缓存。原代码手动按逗号拆分，没有标准 CSV 解析和表头、重复记录校验。

### OQ17：原项目怎样管理 API Key？

**参考回答：**

从本地 `config/secret.yml` 读取，并且该文件在 Git 忽略中，所以不是直接把密钥硬编码提交。但缺少 `.env.example` 和环境变量方案，不方便其他人知道配置结构，也不适合 CI 与容器安全注入。

### OQ18：原模型层使用什么集成？

**参考回答：**

使用 `langchain-community` 中的 `ChatTongyi` 和 `DashScopeEmbeddings`，模型名来自 `config/rag.yml`。后来 Community 集成进入弃用路线，才迁移到 `langchain-openai` 和 DashScope 官方 OpenAI 兼容地址。

### OQ19：原项目为什么在导入工具模块时就可能初始化重量资源？

**参考回答：**

`agent_tools.py` 模块顶部直接执行 `rag = RagSummarizeService()`。只要导入工具模块，就会创建向量存储、检索器和模型链。这会让普通测试和非 RAG 场景也依赖密钥、数据库和外部配置，因此后来改为带锁的延迟初始化并在应用退出时释放资源。

### OQ20：原日志有哪些隐私和排障问题？

**参考回答：**

工具中间件直接记录完整参数，模型前日志可能记录最后一条消息，RAG 链还会打印完整 Prompt 和检索正文。它便于开发调试，但可能保存用户问题和知识内容，而且不同阶段没有统一请求编号。后来改成记录问题编号、阶段、数量、异常和耗时，并最小化正文与参数。

### OQ21：原项目为什么不算前后端解耦？

**参考回答：**

Streamlit 进程直接导入和创建 Agent，Agent 再直接持有模型、Chroma 和工具，没有独立 API 边界。页面、密钥、业务逻辑和资源生命周期耦合在同一进程中，所以后来增加 FastAPI，让前端只通过 HTTP 使用后端。

### OQ22：原项目哪些地方值得保留，而不是全部重写？

**参考回答：**

值得保留的包括清晰的工具划分、RAG 基础闭环、MD5 去重、动态报告 Prompt、本地知识和 CSV 演示数据，以及配置和 Prompt 分文件管理。优化是在这些业务能力上增加工程边界、测试和指标，而不是推翻原目标。

### OQ23：你怎样概括原项目与优化后项目的区别？

**参考回答：**

原项目回答“功能能不能演示”，优化后项目进一步回答“结果能否复现、错误能否拒答、来源能否检查、改动能否量化、服务能否安全部署、失败能否排查”。业务目标基本不变，工程可信度发生了变化。

### OQ24：如果让你只选原项目最先修的三件事，会选什么？

**参考回答：**

第一修复 Chroma 路径和索引唯一性，因为数据源不稳定会影响所有功能；第二移除随机和能力描述不一致的演示数据，保证结果可复现；第三建立依赖、密钥示例和最小测试基线，确保后续每项改动都能安全验证。

## 1. 推荐的项目介绍

### 1.1 30 秒版本

我把一个基于 LangChain 和 Chroma 的扫地机器人客服课程项目，改造成了可复现、可评测、可部署的 Agent + RAG 应用。系统使用 FastAPI 与 Streamlit 前后端解耦，通过 LangGraph 进行工具路由和 SQLite 多轮记忆。RAG 侧使用向量检索、BM25、RRF 和 qwen3-rerank，并提供文件名、PDF 页码、正文引用和资料不足拒答。项目建立了 60 条正负例评测集，重排序后 Hit@3 达到 100%、MRR 为 0.9398，固定用例端到端行为 60/60 通过；同时有 127 项自动化测试、83.62% 覆盖率、Docker Compose 和 GitHub Actions。

### 1.2 90 秒版本

这个项目最初可以演示 Agent 和知识库问答，但存在相对路径生成多份 Chroma、演示数据随机、密钥和运行产物边界不清、无法持久化会话、回答没有可靠来源、没有评测和测试等问题。

我按照 P0 到 P3 分阶段改造。先统一存储路径、固定演示数据、迁移环境变量、增加 SQLite Checkpointer 和依赖锁定；然后实现正文编号、文件名和 PDF 页码引用，以及低分过滤加模型边界判断的两层拒答；再用 FastAPI 解耦 Streamlit，加入非 root Docker Compose、请求编号、耗时日志、安全错误和 CI。最后建立 36 条正例和 24 条负例，对纯向量、BM25 + RRF、qwen3-rerank 做同一数据集的对比。

纯向量 Hit@1/Hit@3/MRR 是 80.56%/94.44%/0.8750，混合检索提升到 88.89%/97.22%/0.9306，重排序后 Hit@3 为 100%、MRR 为 0.9398。查询改写在 4 条困难样本上没有收益，所以没有接入生产。我认为这个项目最有价值的地方不是堆叠组件，而是每项改动都有失败样本、指标、测试和降级策略。

## 2. 项目总览类

### Q1：这个项目解决什么问题？

**参考回答：**

它为扫地机器人领域提供知识问答和演示业务服务。知识问题从本地 TXT/PDF 检索，返回带来源的回答；其他问题由 Agent 选择天气、用户信息和设备使用记录工具。项目重点是让问答可追溯、资料不足时拒答，并把原来的页面演示改造成可测试和可部署的服务。

### Q2：你在项目中最主要的工作是什么？

**参考回答：**

我完成了四类改造：第一是路径、配置、依赖和多轮记忆等基础可靠性；第二是引用、拒答和 60 条评测集；第三是 FastAPI、Docker、日志、错误处理和 CI；第四是 BM25、RRF、重排序和查询改写 A/B。每一阶段都补了自动化测试和变更记录。

### Q3：项目最有技术含量的地方是什么？

**参考回答：**

我认为不是某个库，而是围绕评测做决策。比如单一相似度阈值无法区分正负例，因为负例最高分 0.7608 高于正例最低分 0.6322；因此我保留低分粗过滤，再让模型判断设备范围和资料充分性。又比如查询改写没有提升，所以没有上线。这体现了从失败样本定位召回、排序和生成问题的过程。

### Q4：项目中最难排查的问题是什么？

**参考回答：**

一个典型问题是 Chroma 相对路径导致根目录、`rag` 和 `agent` 下出现多份数据库。表面看是检索不稳定，根因是启动目录改变了相对路径解析。我先备份旧数据，再统一配置为 `storage/chroma`，访问前解析项目绝对路径，并验证 326 个向量和 6 条 MD5 记录都在唯一位置。

### Q5：为什么说这个项目可复现？

**参考回答：**

因为它提供固定版本依赖、`.env.example`、UTF-8 配置、数据导入命令、前后端启动命令、Docker Compose、README 和自动化检查。演示用户、城市和天气也是确定性配置，不会因随机数让同一个演示得到不同结果。

### Q6：为什么不直接做成一个 Streamlit 文件？

**参考回答：**

单文件适合快速原型，但页面重载会影响重量资源生命周期，模型密钥和数据库也与 UI 耦合。拆成 FastAPI 后，前端只使用 HTTP，后端统一管理 Agent、SQLite、Chroma 和密钥，也方便增加其他客户端、接口测试和容器权限隔离。

## 3. RAG 基础与检索类

### Q7：什么是 RAG？

**参考回答：**

RAG 是检索增强生成。先从外部知识库找到与问题相关的片段，再把问题和片段一起交给大模型生成回答。它主要解决私有知识接入和回答依据问题，但不能天然消除幻觉，所以还需要引用、拒答和评测。

### Q8：项目中文档是怎样进入向量库的？

**参考回答：**

程序读取 TXT 和 PDF，保留来源路径与 PDF 页码，用文本切分器生成片段，再调用 `text-embedding-v4` 生成 1024 维向量并写入 Chroma。成功写入后保存文件 MD5，下一次遇到相同内容就跳过，实现幂等导入。

### Q9：为什么必须固定 Embedding 维度？

**参考回答：**

向量库中的同一个集合必须使用一致维度。模型或维度改变后，新向量不能与旧向量正常比较，因此项目显式配置 1024 维，并在变更 Embedding 或距离度量时重建索引，而不是混用旧数据库。

### Q10：为什么使用余弦距离？

**参考回答：**

文本 Embedding 更关注向量方向，余弦距离适合衡量语义方向相似度。迁移后检索排名指标保持不变，但 Chroma 相关性分数越界警告消失。重点是显式声明距离语义并保证接口分数合法，而不是声称余弦一定提高指标。

### Q11：向量检索有什么不足？

**参考回答：**

它对语义改写比较强，但对精确数字、型号、缩写和关键字可能不够稳定。项目中“低于 20% 优先回充”等直接证据没有稳定进入纯向量前三，所以后来增加 BM25 关键词召回。

### Q12：BM25 是什么？

**参考回答：**

BM25 是基于词项匹配的排序算法，会综合词频、逆文档频率和文档长度。通俗地说，查询中的稀有关键词如果出现在某个文档中，会提高该文档排名。它与向量检索互补，而不是替代关系。

### Q13：中文没有空格，你怎样给 BM25 分词？

**参考回答：**

项目采用轻量的中文双字词元，并保留英文、数字和符号词元。这样不增加大型分词依赖，也能捕捉“电量”“低于”“20%”等局部匹配。它适合当前小型领域知识库，但更复杂语料可以评估专业分词器。

### Q14：为什么不直接把向量分数和 BM25 分数相加？

**参考回答：**

两者的分数定义和范围不同，直接相加没有稳定意义。项目使用 RRF，只根据各自排名计算倒数排名分数，因此不需要先校准两种分数尺度。

### Q15：RRF 的公式是什么？

**参考回答：**

对每个文档，把它在各检索列表中的 `1/(k + rank)` 相加。`k` 是平滑常数，rank 越靠前贡献越大。项目使用文档 ID 去重，并通过网格搜索选出 `k=10`。

### Q16：混合检索参数是拍脑袋选的吗？

**参考回答：**

不是。我比较了 2 种向量候选数、3 种 BM25 候选数和 5 种 RRF 常数，共 30 组配置，并用同一批 36 条正例比较 Hit@1、Hit@3、MRR、提升和退化样本。最终选择向量 10、BM25 20、RRF 常数 10。

### Q17：为什么混合检索后还需要重排序？

**参考回答：**

混合召回解决“候选是否被找到”，但 RRF 只看两路排名，不能深入判断片段是否完整回答问题。项目候选 Recall@10 已是 100%，但有些直接证据仍在第 4 或第 6，所以用 qwen3-rerank 对 10 条候选做语义重排，再选 Top-3。

### Q18：重排序取得了什么效果？

**参考回答：**

混合 Top-3 的 Hit@3 是 97.22%、MRR 0.9306；重排序后 Hit@3 达到 100%、MRR 0.9398。低电量 20% 和完整 HEPA 周期证据都被提升到第一名。Hit@1 仍是 88.89%，所以我不会把它描述成所有指标都大幅提高。

### Q19：如果重排序服务失败怎么办？

**参考回答：**

捕获远程请求、响应格式和下标异常，记录不含用户正文和密钥的警告，然后退回 RRF Top-3。这样重排序是增强项，而不是整个知识问答的单点故障。

### Q20：为什么最终只给模型 Top-3？

**参考回答：**

融合阶段保留 Top-10 是为了高召回，重排序后只给 Top-3 是为了减少无关上下文、Prompt 长度和模型干扰。候选 Recall@10 已达到 100%，所以先在较大候选池中找全，再压缩到更高质量上下文。

### Q21：为什么查询改写没有上线？

**参考回答：**

我对 4 条固定困难样本做了 A/B，原查询和改写查询 Hit@1 都是 0/4，MRR 都是 0.4583，四条全部不变。当前问题表达已经明确，候选 Recall@10 也达到 100%，改写没有补充新召回信息，却增加一次模型调用，所以只保留实验脚本。

### Q22：什么时候查询改写可能有用？

**参考回答：**

真实问题如果包含多轮指代、省略设备名称、口语缩写、错别字或多个意图，改写可能把隐含条件补全。应先收集这些真实失败样本，再扩充固定评测集重新 A/B，而不是直接打开功能。

## 4. 引用、拒答与幻觉类

### Q23：回答来源是模型生成的吗？

**参考回答：**

不是完全交给模型。服务端根据检索 Document 元数据建立来源编号，模型只在正文引用编号，文末文件名和 PDF 页码由程序映射和追加。这样比让模型自己写来源可靠。

### Q24：为什么只显示正文实际引用的来源？

**参考回答：**

Top-3 是候选证据，不代表模型实际使用了全部三份。如果全部列出，用户会误以为每份都支持答案。项目解析正文编号，只显示被使用的来源，同时保留原始编号，避免重新编号造成错引。

### Q25：怎样实现资料不足拒答？

**参考回答：**

第一层用 0.20 分数过滤明显无关片段；第二层在 System Prompt 中检查设备对象、时效、问题范围和证据充分性。没有片段时不调用模型，直接返回统一拒答；有相似片段但不足时，模型返回内部标记，服务层再转换为统一拒答。

### Q26：为什么不把相似度阈值设高一点？

**参考回答：**

因为正负例分数重叠。正例最低 Top-1 是 0.6322，负例最高是 0.7608，不存在一个阈值能同时保留所有正例并过滤所有负例。单一阈值只能做粗过滤，不能承担业务范围判断。

### Q27：高分负例是什么样的？

**参考回答：**

例如手持吸尘器吸力下降，会召回扫地机器人清理滤网和风道的高相似片段；主板电压诊断也会匹配故障排除文本。它们词义相似，但设备范围或维修深度超出知识库，所以必须拒答。

### Q28：怎样评价幻觉是否完全解决？

**参考回答：**

不能说完全解决。项目通过检索证据、System 边界、统一拒答和来源引用降低风险，并在固定 60 条用例上验证行为，但没有为每条回答做完整人工事实标注。更准确的说法是“在当前评测边界内显著增强了可追溯性和拒答能力”。

## 5. Agent 与多轮记忆类

### Q29：Agent 如何选择工具？

**参考回答：**

把工具描述和当前消息交给支持工具调用的聊天模型，模型在首轮返回 `tool_calls`。LangGraph 执行所选工具，再把结果返回模型生成最终答案。项目单独用 12 条用例评估第一次工具选择，避免最终答案掩盖路由错误。

### Q30：为什么工具描述很重要？

**参考回答：**

模型主要根据工具名称、描述、参数和 Prompt 选择工具。如果描述含糊，例如没有说明天气是演示数据、RAG 只覆盖扫地机器人，就容易错误路由或夸大能力。因此工具描述也是 Agent 的接口设计。

### Q31：为什么演示数据不能随机？

**参考回答：**

随机用户和月份会让相同输入得到不同上下文，测试不可重复，演示也可能查不到 CSV 记录。确定性数据更容易复现，且明确标注演示性质，避免冒充真实业务系统。

### Q32：多轮记忆是怎样持久化的？

**参考回答：**

LangGraph 使用 SQLite Checkpointer 按 `thread_id` 保存图状态。FastAPI 进程复用一个 Agent 和 SQLite 连接，URL 中的 UUID 用于恢复同一会话；应用关闭时通过生命周期钩子释放连接。

### Q33：为什么使用 UUID4？

**参考回答：**

UUID4 随机性高、碰撞概率低，适合作为本地会话键。后端还校验它的格式和版本。但 UUID 只是标识，不是认证；公开系统仍需要登录、授权和会话过期。

### Q34：为什么不用内存字典保存会话？

**参考回答：**

内存字典在进程重启后丢失，也不适合验证恢复能力。SQLite 对单机演示足够轻量，能够展示持久化和会话隔离；如果将来多实例部署，再迁移 PostgreSQL。

### Q35：为什么暂时不做多 Agent？

**参考回答：**

当前任务只有知识问答和几个简单业务工具，单 Agent 路由已经在 12 条用例上全部通过。多 Agent 会增加角色协调、状态传递、延迟和测试成本，却没有已观察到的问题需要它解决。

## 6. FastAPI、前端和错误处理类

### Q36：FastAPI 提供哪些核心接口？

**参考回答：**

提供健康检查、聊天和会话历史接口。聊天接口接收 `thread_id` 和消息，调用共享 Agent 并返回答案；历史接口从 LangGraph 状态中重建用户和最终助手消息；健康接口只验证服务存活，不调用外部模型。

### Q37：为什么前端不直接访问模型 API？

**参考回答：**

这样模型密钥只保留在后端，业务逻辑和数据访问也集中在服务端。前端只处理 HTTP 和展示，便于测试、替换客户端，并减少权限范围。

### Q38：如何防止后端异常泄漏给用户？

**参考回答：**

Agent 边界记录完整服务端异常并生成问题编号，FastAPI 转换为安全的 502 JSON，前端只展示通用提示和编号。未知 HTML、SDK 堆栈和本地路径不会原样显示。

### Q39：请求编号有什么用？

**参考回答：**

一次请求会经历 FastAPI、Agent、模型和工具多个阶段。共享问题编号可以在日志中关联这些记录，而不需要记录用户完整问题。用户反馈编号后，开发者能定位同一次失败。

### Q40：为什么要限制消息长度？

**参考回答：**

防止异常大请求造成 Token 浪费、延迟或资源滥用，也让 API 契约更明确。当前上限是 4000 字符，这是项目演示边界，不是模型最大上下文长度。

## 7. Docker 与部署类

### Q41：Dockerfile 为什么使用非 root 用户？

**参考回答：**

即使容器进程被利用，普通用户的权限也更小。项目构建时创建 `appuser`，并提前创建日志和存储目录、授予必要权限，而不是为了省事一直用 root。

### Q42：为什么 FastAPI 和 Streamlit 使用同一镜像？

**参考回答：**

二者依赖同一份项目代码和 Python 包，使用同一镜像可以减少重复构建。Compose 通过不同启动命令、环境变量和挂载把它们分成两个服务。

### Q43：为什么只有 API 容器挂载存储和密钥？

**参考回答：**

这是最小权限原则。Streamlit 只需要调用后端，没有理由读取 Chroma、SQLite、日志或 API Key。减少前端容器权限，也缩小数据泄漏范围。

### Q44：Docker 健康检查为什么不能调用大模型？

**参考回答：**

健康检查会频繁执行。如果调用外部模型，会产生费用，也会把网络或供应商波动误判为容器自身故障。项目只检查本地 FastAPI 和 Streamlit 健康端点。

### Q45：容器重建后数据为什么还在？

**参考回答：**

Chroma、SQLite 和日志通过宿主机目录挂载，不保存在容器可写层中。删除和重建容器不会删除这些宿主机数据；但执行更广泛的删除操作前仍应检查挂载位置。

## 8. 测试与持续集成类

### Q46：项目有哪些测试层次？

**参考回答：**

包括纯函数单元测试、带假依赖的服务测试、FastAPI 路由与生命周期测试、前后端架构边界测试、Docker 配置测试、评测脚本测试，以及需要真实模型的手工冒烟和全量评估。默认测试不访问真实 API。

### Q47：覆盖率 83.62% 说明什么？

**参考回答：**

它说明纳入统计的核心模块语句中，83.62% 在测试时被执行过。它不能证明这些代码全部正确，也不能代替边界用例设计。项目同时关注关键行为断言，而不是只追求覆盖率数字。

### Q48：为什么 CI 门禁只设 60%，本地却有 83.62%？

**参考回答：**

60% 是防止覆盖率明显倒退的最低门槛，不是项目目标值。部分入口和真实外部调用不适合在 CI 中执行。实际覆盖率高于门槛，后续可以随稳定性逐步提高，但不应为了数字写没有断言价值的测试。

### Q49：为什么真实模型评测不放进默认 CI？

**参考回答：**

真实模型评测有费用、网络依赖和非确定性，还需要真实密钥。CI 使用占位环境变量和 Mock，保证每次提交稳定、快速、安全；真实评测在关键改动后人工运行并保存结果。

### Q50：你怎样测试外部 HTTP 调用？

**参考回答：**

重排序器和前端 HTTP 客户端支持注入 MockTransport 或假客户端，测试正常响应、超时、连接失败、非法 JSON、错误下标和降级行为，不访问真实网络。

### Q51：Ruff 检查什么？

**参考回答：**

当前基线主要检查导入顺序、语法级问题、未定义名称和一部分基础风格。它不替代测试和类型检查，也没有为了追求“规则越多越好”一次性开启全部规则。

## 9. 评测指标类

### Q52：Hit@1 和 Hit@3 有什么区别？

**参考回答：**

Hit@1 看正确来源是否排第一，直接影响模型最先看到的证据；Hit@3 看正确来源是否进入前三，更接近最终上下文是否包含答案。两者结合可以区分“完全没召回”和“召回了但排序不够好”。

### Q53：MRR 为什么有用？

**参考回答：**

Hit@3 只判断进没进前三，不区分第一和第三。MRR 使用正确来源排名的倒数，第一名贡献 1，第二名 0.5，第三名约 0.333，所以能反映整体排名位置。

### Q54：为什么评测集需要负例？

**参考回答：**

只有正例会鼓励系统尽量回答，却无法衡量它是否会对知识库外问题编造答案。困难负例用于验证知识边界，包括实时信息、相邻设备和高风险维修等。

### Q55：60/60 是否说明准确率 100%？

**参考回答：**

只能说固定用例的预期行为准确率是 100%。正例条件是生成有效回答并带可映射来源，负例条件是统一拒答；它没有对回答中的每个事实都做人工正确性判定。

### Q56：引用命中率和引用一致率有什么不同？

**参考回答：**

预期来源引用命中率按用例统计：一条正例只要至少引用一份人工标注来源就算命中。正文引用标注一致率按所有引用统计：每一条正文引用是否出现在当前人工标注中。前者是 100%，后者是 78.18%。

### Q57：为什么 78.18% 不能直接叫引用准确率？

**参考回答：**

因为人工标注可能只列核心来源，没有穷举所有有效辅助来源。未命中标注不一定是错误引用，所以我用“与当前人工标注一致率”这个更严格的名称，并说明需要片段级证据标注才能进一步判断。

### Q58：P95 为什么比平均响应时间更有意义？

**参考回答：**

平均值容易掩盖少量很慢的请求。P95 表示约 95% 请求不超过该耗时，更能观察尾延迟。但它仍受本机网络、模型服务和样本数影响，应说明测试环境。

### Q59：为什么单独评估工具路由？

**参考回答：**

最终答案正确不代表第一步工具选择正确，模型可能通过后续信息侥幸补救。路由评测只检查首轮 `tool_calls`，不执行工具，因此能隔离 Agent 的决策能力。

### Q60：Token 指标统计完整请求了吗？

**参考回答：**

没有，只统计第一次工具路由模型调用。平均总 Token 是 2184.75、P95 是 2407。Embedding、重排序、工具执行和最终回答没有计入，所以我不会把它称为完整请求成本。

## 10. 工程决策与开放题

### Q61：如果给你更多时间，下一步做什么？

**参考回答：**

优先收集真实用户问法，把评测集扩充到约 100 条并增加片段级直接证据标注；然后补完整请求 Token/成本和浏览器端到端测试。公开部署前还需要认证、授权、限流、TLS、会话过期和集中式监控。

### Q62：如果知识库扩大十倍，你会怎么改？

**参考回答：**

先重新测召回率和延迟，再考虑索引分区、元数据过滤、增量更新和服务化向量数据库。BM25 目前在内存中构建，小规模合适，规模变大后需要持久化倒排索引。不能只因为数据变大就直接换技术，仍要用基线定位瓶颈。

### Q63：如果要支持多实例部署，当前哪里不够？

**参考回答：**

SQLite Checkpointer 和本地 Chroma 都是单机方案，多实例之间不能共享一致状态。应迁移到 PostgreSQL 等共享检查点和服务化向量数据库，同时增加分布式追踪、集中日志和统一认证。

### Q64：如果模型供应商不可用怎么办？

**参考回答：**

当前重排序已经有 RRF 降级，但聊天和 Embedding 仍依赖 DashScope。生产环境可以增加超时、有限重试、熔断、模型备用路由和缓存，同时确保降级不绕过知识边界。

### Q65：为什么没有使用 Ragas？

**参考回答：**

我评估过 Ragas 0.4.3，但它在当前 `langchain-community 0.4.2` 环境中仍导入已移除的 VertexAI 路径，运行时无法导入。为了一个评测工具降级稳定的 LangChain 1.x 不划算，因此恢复环境并保留现有确定性检索、行为、引用和性能评测。对当前实习项目，自研完整 LLM-as-a-Judge 的新增价值也有限。

### Q66：为什么没有自研 Faithfulness 和 Answer Relevancy？

**参考回答：**

它们需要额外评审模型调用、原子事实拆分、结构化输出和一致性校准。若生成模型和评审模型相同，还存在自评偏差。当前项目已经用 60 条正负例、来源命中和人工困难样本复核证明核心能力，所以我把它列为可选扩展，没有为了指标名称增加冗余代码。

### Q67：这个项目最大的不足是什么？

**参考回答：**

评测集仍是 60 条人工设计问题，来源标注主要在文件级，不代表真实流量和全部片段级事实。系统也没有认证和多实例能力。因此它是一个工程化较完整的单机实习项目，而不是可以直接面向真实用户的生产客服。

### Q68：如果面试官说你的数据集太小，怎么回答？

**参考回答：**

我会承认 60 条不能代表完整分布，它的价值是建立可重复基线并覆盖主要知识主题和困难边界。下一步不是盲目生成更多相似问题，而是收集真实失败问题、按主题和边界分层扩充，并增加片段级证据标注。

### Q69：为什么不微调模型？

**参考回答：**

当前主要问题是私有知识召回、证据排序和知识边界，微调不会自动更新知识，也不能替代来源追溯。先把 RAG 数据和评测做好，只有收集到稳定的表达、路由或格式失败模式后，才评估微调收益。

### Q70：你怎样证明自己不是只会调用框架？

**参考回答：**

我会重点讲框架之外的决策和验证：相对路径根因、幂等写入顺序、正负例分数重叠、中文 BM25 词元、RRF 参数搜索、候选召回与排序瓶颈区分、重排序降级、引用编号映射、资源生命周期和查询改写的否定性实验。这些问题换一个框架仍然存在。

## 11. 容易说错的话

面试时避免以下表述：

| 不准确的说法 | 更准确的说法 |
| --- | --- |
| “我的 RAG 准确率是 100%” | “固定 60 条用例的预期行为是 60/60 通过” |
| “引用准确率是 78.18%” | “正文引用与当前人工来源标注一致率为 78.18%” |
| “覆盖率 83.62%，所以代码基本没 Bug” | “核心模块语句覆盖率为 83.62%，并对关键边界做了行为断言” |
| “用了查询改写优化检索” | “做过查询改写 A/B，但没有收益，因此没有接入生产” |
| “Token 成本是 2184.75” | “首步工具路由模型调用平均为 2184.75 Token，不含后续链路” |
| “Docker 后就是生产级系统” | “Docker Compose 支持本地可复现部署，认证、多实例和监控仍是限制” |
| “高相似度就可以回答” | “相似度只做粗筛，能否回答还要判断对象、时效和资料充分性” |

## 12. 回答追问的通用结构

遇到没有背过的问题，可以按下面四步回答：

1. **现象或目标**：当时遇到了什么问题；
2. **选择与理由**：为什么采用这个方案；
3. **验证**：用什么测试、指标或失败样本证明；
4. **边界**：它没有解决什么，下一步是什么。

例如回答“为什么加重排序”：

> 混合检索已经把预期来源全部召回到 Top-10，但低电量和 HEPA 的完整证据还在第 6 和第 4，说明瓶颈从召回变成排序。我用 qwen3-rerank 对融合候选重排，最终两条证据都升到第一，Hit@3 从 97.22% 到 100%、MRR 从 0.9306 到 0.9398。重排序服务失败时会降级到 RRF，因此没有把外部服务变成单点故障。Hit@1 没有继续提升，所以我不会夸大它的效果。

这类回答比只说“因为重排序更准确”更可信，也更能体现你真正理解了项目。
